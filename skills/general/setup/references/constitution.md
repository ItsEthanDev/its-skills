# Constitution

Establish a constitution when the user wants a consolidated owner for durable project constraints. Preserve existing governance and policy owners. A scoped request can establish or amend a constitution without setting up the rest of the project.

Ask what bounds the user already has in mind. Distinguish accepted constraints from current implementation and feature-specific requirements. A small constitution with a few agreed rules is useful; do not invent principles to fill the template or create an empty claim of authority.

Use the constitution seed template to establish the document's operating contract: its scope, how contributors assess compliance and surface conflicts, who may approve amendments, how ratification is recorded, and which dependent documents and checks must be reconciled. Confirm these choices with the user. Preserve an existing amendment process and obtain its required approval before changing governance.

For help drafting or amending the actual constraints, use `constitute` when available. It owns the reusable constraint-writing method; setup establishes the project's chosen home and self-contained governance procedure. The resulting constitution must not require that skill to be installed to apply or amend its rules.

Replace every retained placeholder before ratification. Make draft versus ratified status explicit; an agent's proposal is not adopted policy. Establish the maintainer or approval role rather than assigning that authority to the agent.

Keep agent-specific operating instructions in the applicable agent entry point. Link the constitution from the documentation index and establish when contributors must read it. A later setup run can propose migration, but follows the existing ratification procedure rather than overwriting it.
