# Bootstrap and Migration

Use this branch when a project has no documentation or its existing documentation does not yet have clear owners. Read applicable project instructions before changing files. Treat a request to adopt this system as a direction to organize documentation, not as permission to invent product intent or change code, deployments, or external services.

1. Inventory existing README, specs, plans, tasks, domain context, contracts, guides, and policy. Inspect the relevant code, tests, configuration, commands, and available project history to identify current behavior and real entry points. Report which claims are observed facts, existing accepted decisions, or uncertain interpretations. Do not infer live deployments or configured external integrations from code alone.
2. Map coherent feature outcomes and each durable claim to an owner under [ARTIFACT-MODEL.md](ARTIFACT-MODEL.md). Preserve useful project conventions where their ownership is clear; otherwise use the conventional names and locations in [FEATURE-ARTIFACTS.md](FEATURE-ARTIFACTS.md). A code feature is not automatically a product feature that needs its own directory or specification.
3. Ask the user focused questions in batches when purpose, intended behavior, scope, feature boundaries, or consequential design cannot be established from authority. Offer the observed alternatives and their sources. Do not turn current implementation or old prose into a new accepted target without direction. Continue independent, unambiguous documentation work while awaiting answers; keep unresolved choices visible rather than guessing.
4. Create or reconcile only useful artifacts. Write the user's confirmed target into living specs where it adds meaning beyond code; document verified current behavior in human guides when useful; reference declarations that already own exact details. Remove obsolete or duplicate legacy prose after its information has an owner, not merely to match a directory layout. Do not fabricate decision history or create empty `spec.md`, `plan.md`, or `tasks.md` files.
5. Verify references, commands, and claims against their sources. Use [PROJECT-DOCUMENTATION.md](PROJECT-DOCUMENTATION.md) for developer setup and operational evidence. Record what remains unverified and the decisions that still need the user's direction. The result should be coherent without implying it was always organized this way.
